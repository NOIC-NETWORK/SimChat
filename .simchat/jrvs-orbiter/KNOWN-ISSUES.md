# JRVS-7B 已知问题清单

适用权重：`televideo-ai/JRVS-7B-1.2.2:q4_k_m`（Qwen3-8B 基座，上游 SFT+LoRA 已合并）。
证据：`eval/cases_kirara.jsonl` 30 条用例，2026-11-19 四组配置（A–D，见 `README.md`）。

## 一、原版权重缺陷

这些是上游 SFT 遗留的能力问题，不是提示词或宿主解析造成的；提示层无法修复，只能靠重训/换基座。

| 问题 | 证据 | 处理方向 |
| --- | --- | --- |
| 算术错误：把 2 的 10 次方答成 5,874,693,579 | C 组实测（`eval/kirara_protocol_modelfile.json`） | 原版权重缺陷；SFT 需要加入可验证的算术/推理样本，或换更强基座 |
| 翻译题输出无关代码 | C 组实测 | 原版权重缺陷；上游语料分布偏移，SFT 需要干净的双语翻译样本 |

## 二、协议/格式缺陷（提示层已到上限，必须靠 SFT）

模型没有见过宿主要求的委派格式；提示词叠加协议不会削弱触发词，但也不能修好格式。

| 问题 | 现状 | 处理方向 |
| --- | --- | --- |
| 委派格式只到 1~2/6 | A/B/D 组 1/6，C 组 2/6；提示层已到上限 | SFT 协议语料，目标 delegation ≥ 90% |
| 寒暄前缀（如“好的，主人sama”） | 宿主解析器已容忍短前缀，但模型仍持续输出 | 宿主容错只是兜底，SFT 训练“委派指令单独成行、无前后缀” |
| 代码块包裹委派指令 | 模型会把 `/@...` 包进 ``` 代码块 | SFT 协议语料；宿主不做猜测式剥离 |
| `-prompt=` 写法 / 塞进同一行 | README 要求的 `-prompt "..."` 常被写成 `-prompt=...` 或同行拼接 | SFT 协议语料，按原案格式逐条对齐 |

## 三、不是缺陷

- **触发词身份**：路径 1（派生标签）与路径 2（HTTP 显式 system）都能稳定激活 Kirara；3×6 重复结果为 A 88.9%、B 94.4%、C 100%、D 88.9%，差异在采样噪声内。
- **协议叠加**：`system_kirara_protocol.txt` 第一行仍是 `Kirara`，叠加后触发强度不降反升（C 组 18/18），可以继续使用。

## 四、达标线（重训后复测）

- 触发词身份：6/6。
- delegation：≥ 90%。
- simple 不误委派：≥ 95%。
- 算术与翻译：不再复现上述两类错误。

> 训练与量化链路已在 `train/`、`quant/` 备好；语料来源未确认前不扩数据集。
> `ollama-models/` 是本机隔离测试缓存，不进入版本控制。
