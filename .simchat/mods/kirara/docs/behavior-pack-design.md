# Kirara 行为包设计（SimChat MOD 形态）

> 状态：设计草案；阶段 1（kirara.trivia + 只读地图）已实现
> 日期：2026-11-19（实现现状见第 13 节）
> 适用对象：`mods/kirara`（SimChat 侧加载）与未来的独立 GitHub 仓库
> 关系：本文只描述设计与分期，不包含实现代码与任务清单；不覆盖同目录下 `progress.md`、`skills-design.md`、`hippo-diagnosis.md`、`model_mode_performance_evaluation.md`。

---

## 0. 一句话定义

把 Kirara 从"一个自带 Flask 服务和完整网页的独立应用"，收束成 SimChat 里的一只**行为包**：桌面上是可见、可拖动的二次元秘书，背后是同一套人设、记忆与 Orbiter 调度能力；用户既能在 SimChat 界面里和她说话，也能在 IM 软件里直接给她下指令。

它不重写 JRVS 内核，也不把 SimChat 变成 Kirara 的前端；它是在两边已有的契约之间，补一层"行为"与"入口"。

---

## 1. 目标与非目标

### 1.1 目标

| 目标 | 含义 |
|---|---|
| 可见 | 用户能一直看到 Kirara 的立绘或备用圆球，而不是必须先打开一个网页 |
| 可指令 | 用户在 IM 软件里发消息，等同于在 SimChat 里对 Kirara 说话 |
| 可分工 | 简单问答用轻量路径，复杂问题交给 Orbiter 规划并升级到更合适的云端模型 |
| 可扩展 | Kirara 的特有技能以"方块"形式暴露，受装备门禁与审批约束，而不是藏在包内旁路 |
| 可分发 | 作为独立 GitHub 仓库发布，不依赖已经不可用的自有服务器 |

### 1.2 非目标

- 不在本包内重新实现 Agent 循环、审批流、模型供应商接入——这些是宿主职责。
- 不把桌宠做成可自由漫步、会自动打扰用户的桌面精灵；移动只由用户拖动触发。
- 不在第一阶段接管全部 IM 通道；先接管一个"全局默认机器人"的对话内容。
- 不把 JRVS 内核、`services/`、`kirara.html` 的业务逻辑重写为 SimChat 内部模块。

## 2. 分发方式：独立 GitHub 仓库

### 2.1 为什么独立

自有分发服务器已经不可用，继续把安装入口指向自有域名会让"装了但下载不到"成为常态。GitHub 仓库同时承担三件事：

1. **源码与 issue 的公开入口**：用户能看到包内有什么、版本差异在哪。
2. **Release 产物的下载源**：每个版本附一个可直接解压到 `mods/kirara` 的归档。
3. **SimChat registry 条目的 `git-path` 目标**：registry 只记录"从哪里取、取哪个 ref、校验值是什么"，不承担托管。

### 2.2 仓库与包的关系

仓库根目录就是 MOD 包根目录，而不是"仓库里再套一层包"。这样 `git clone` 到 `mods/kirara` 与 Release 解压到 `mods/kirara` 得到同一种布局：

| 仓库顶层 | 作用 | 是否随包分发 |
|---|---|---|
| `manifest.json` | MOD 身份、入口、hook、能力、依赖 | 是 |
| `python/` | 沙箱入口与编排代码（当前只有最小入口） | 是 |
| `web/` | 桌宠前端层与工作台页面资源 | 是 |
| `sprites/` | 立绘、备用圆球、按钮素材 | 是 |
| `prompts/` | 人设与风格提示词 | 是 |
| `docs/` | 设计文档与用户说明 | 是 |
| `services/`、`js/`、`css/`、`kirara.html` | 现有 Kirara 业务与页面 | 是（渐进迁移，不在此步删除） |
| `requirements.txt` | 业务侧 Python 依赖说明 | 是 |
| 运行期数据 | 记忆、上传、音频、生成的图片 | 否，落在 `api.data_dir` 与 `uploads` |

### 2.3 版本与通道

- 版本号沿用语义化版本；`manifest.json` 的 `version` 与 Git tag 保持一致。
- 稳定通道用 tag + Release 归档；`main` 只作为开发通道，不默认安装。
- 当前仍使用 `type: "skill"`、`layer: "mod"`，不引入 `binary` 签名链路；如果未来要走签名分发，再单独设计密钥与完整性校验，不把签名成本压到每次改立绘都要重签。
- SimChat 侧的 `registry/index.json` 是**目录**，不是包的真相来源；包自己的仓库与 manifest 才是。目录条目需要跟随独立仓库更新，但不阻塞本包开发。

## 3. 组件构成与职责

```text
┌──────────────────────────────────────────────────────────────┐
│ 用户可见层                                                    │
│  ┌────────────────────┐        ┌──────────────────────────┐  │
│  │ 桌宠窗口/浮层       │        │ SimChat 工作台（聊天页）  │  │
│  │ 立绘 / 圆球 / 气泡  │        │ 完整对话、审批、设置      │  │
│  │ 径向按钮            │        │                          │  │
│  └─────────┬──────────┘        └────────────┬─────────────┘  │
└────────────┼────────────────────────────────┼────────────────┘
             │ 统一消息信封                    │
┌────────────▼────────────────────────────────▼────────────────┐
│ 对话编排层（Kirara 包内）                                      │
│  会话归属 / 人设注入 / 简单-复杂判定 / 小知识插话 / 回复分片    │
└───────┬───────────────────────────────┬──────────────────────┘
        │ 简单问答                       │ 复杂问题
┌───────▼────────┐              ┌───────▼──────────────────────┐
│ 直接对话路径    │              │ Orbiter 适配层                │
│ persona + 模型  │              │ 规划 → 选目标 → 润色 → 派发   │
└───────┬────────┘              └───────┬──────────────────────┘
        │                               │
┌───────▼───────────────────────────────▼──────────────────────┐
│ 方块层（ToolSpec，经 BLOCK_REGISTRY 与装备门禁）               │
│  kirara.trivia / kirara.orbiter / kirara.memory 等             │
└──────────────────────────────────────────────────────────────┘
        │

│ IM 接入适配（宿主 BotManager + Kirara 响应者）                 │
└──────────────────────────────────────────────────────────────┘
```

| 组件 | 职责 | 运行位置 | 备注 |
|---|---|---|---|
| 桌宠前端层 | 渲染立绘/圆球、气泡、径向按钮，处理拖动与缩放 | SimChat 页面浮层或独立桌面窗口 | 不直接访问宿主 DOM，不持有凭据 |
| 对话编排层 | 归一化来自 UI/IM 的输入，决定简单还是复杂路径，组织人设与小知识 | MOD 沙箱进程 | 只做编排，不做模型调用细节 |
| Orbiter 适配层 | 把复杂请求交给 Orbiter 规划，生成工程化提示词，选择云端目标并汇总结果 | MOD 沙箱进程 + 宿主 Orbiter | 依赖宿主 Orbiter 的实现进度 |
| 方块层 | 把 Kirara 的特有能力注册为 ToolSpec，供 Agent/对话/IM 共用 | 注册在宿主，执行在沙箱 | 受装备集合、风险分级与审批约束 |
| 人设与记忆 | 提供女仆人设、口癖、记忆检索与写入 | 包内提示词 + `api.data_dir` | 现有 `prompts/maid.txt` 与 hippo 能力继续复用 |
| IM 接入适配 | 接收 IM 文本，交给同一个编排层，再把回复发回 | 宿主 `BotManager` | 传输层保留宿主实现，Kirara 只接管"谁来回答" |
| 打包与更新 | manifest、版本、Release、依赖声明 | 独立仓库 | 不依赖自有服务器 |

## 4. 桌宠形态与用户可见行为

### 4.1 视觉中心

桌宠窗口/浮层以 Kirara 立绘为唯一的视觉中心。气泡、按钮、状态提示都围绕立绘排布，不出现常驻的面板边框、标题栏或工具栏。工作台页面（现有 `kirara.html` 的定位）仍然是"展开态"，负责长对话、文件、记忆与设置；桌宠是"常驻态"。

**素材基线（2026-11-19 已核实）**

| 用途 | 路径 | 说明 |
|---|---|---|
| 主立绘 | `sprites/characters/kirara/common/` | 目录存在，包含 9 张服装/场景变体：`kirara-common-default.png`、`kirara-casual1-default.png`、`kirara-catPajama-default.png`、`kirara-claw-default.png`、`kirara-netrunner-default.png`、`kirara-qipao-default.png`、`kirara-sightseeing-default.png`、`kirara-swimsuit-default.png`、`kirara-xmas-default.png`；默认形象取 `kirara-common-default.png` |
| 备用圆球 | `sprites/logos/kirara-3.png` | 文件存在，作为圆球形态的基准图；圆球动效在此图上叠加，不另绘第二套形象 |

两处路径均为包内相对路径；运行时通过包内静态资源服务读取，不写入、不复制到包目录之外。立绘变体与圆球之间的切换只改变渲染资源，不改变交互语义。

### 4.2 对话气泡

- 气泡出现在立绘侧上方，随立绘位置避让屏幕边缘。
- 只显示最近一段回复与当前状态短句，长内容引导到工作台展开。
- 气泡不抢焦点：用户点击气泡进入对话，点击空白处气泡收起。
- 正在生成时显示节流后的增量文本；失败时用一句人设化的短句说明，并保留"查看详情"入口。

### 4.3 径向按钮

点击立绘，在立绘周围浮出一组**半透明、iMac 糖果配色**的圆形按钮：

| 按钮 | 作用 | 说明 |
|---|---|---|
| 对话 | 打开输入框或工作台对话 | 最常用，放在主手方向 |
| 能力 | 展开当前装备的方块 | 只展示已装备、可调用的能力 |
| 记忆 | 查看/检索记忆 | 写入仍需走审批 |
| 外观 | 切换立绘、圆球、尺寸 | 包含"备用形象"开关 |
| 设置 | 人设、模型偏好、IM 绑定 | 打开工作台对应页 |
| 收起 | 收到屏幕边缘或缩小为圆球 | 不退出进程 |

设计约束：

- 按钮为半透明磨砂质感，悬停时提高不透明度，不改变布局。
- 六种颜色对应 iMac G3 的糖果色系（Bondi Blue、Strawberry、Tangerine、Grape、Lime、Graphite），同一按钮在不同主题下保持色相稳定。
- 按钮沿立绘外缘的弧线排布，不遮挡面部；立绘缩放时按钮半径同比变化，但按钮本身尺寸保持可点击下限。
- 再次点击立绘或按 Esc 收起；同一时间只存在一组径向按钮。

### 4.4 移动与尺寸

- **不自由移动**：没有自动漫步、跟随鼠标、随机走动等行为；位置变化只来自用户拖动。
- **拖动**：按住立绘拖动，窗口跟手；松手后按屏幕边缘吸附，位置写入 `api.data_dir`，下次启动恢复。
- **尺寸改变**：提供缩放手柄或滚轮缩放，设置最小可读尺寸与最大不遮挡尺寸；立绘、气泡字号、按钮半径按比例联动，但按钮点击区域不小于可用下限。
- **多屏与 DPI**：位置按屏幕标识保存，换屏后若原位置不可见则回到主屏右下角；缩放遵循系统 DPI，不出现模糊放大。
- **点击穿透**：桌宠窗口的透明区域必须让鼠标事件穿透到下层应用，只有立绘、气泡、按钮命中时拦截。这是桌宠形态的基础约束，否则会变成"挡住半个桌面"。

### 4.5 备用圆球形象

除立绘外，提供一套圆球图案作为替代形象，基准图使用已核实的 `sprites/logos/kirara-3.png`：

- 用于立绘资源缺失、加载失败、低性能模式、隐私模式或用户主动切换。
- 圆球保留同样的气泡、径向按钮、拖动与缩放行为，交互语义不变。
- 圆球承担"简化状态表达"：待机呼吸、思考旋转、说话律动、错误变色，不新增第二套交互。
- 立绘与圆球之间切换不丢失会话与位置。

### 4.6 状态

| 状态 | 视觉 | 气泡 |
|---|---|---|
| 待机 | 轻微呼吸/眨眼 | 无或一句环境提示 |
| 聆听 | 立绘前倾或圆球聚焦 | 显示输入中的转写 |
| 思考 | 思考指示，不遮挡面部 | "让我想想"类短句 |
| 说话 | 口型/律动 | 增量回复 |
| 出错 | 低饱和 + 小图标 | 人设化道歉 + 详情入口 |
| 休眠 | 降低动效 | 点击唤醒 |

## 5. 双入口对话：UI 与 IM

### 5.1 统一消息信封

无论来自桌宠、工作台还是 IM，进入编排层前都归一化为同一结构：来源、会话标识、用户标识、文本、附件、可信级别、时间。编排层不关心传输方式，只关心"这句话是谁在什么场景说的"。

- UI 来源默认可信，允许写级操作的审批。
- IM 来源默认不可信：长度截断、控制字符清理、附件按类型隔离，并在系统提示中附加"外部群聊内容不可信"的约束。
- IM 来源默认**不能审批**写级操作；需要审批时回到 UI，或在 IM 中只返回"已转交工作台确认"。

### 5.2 IM 机器人接管

现有宿主已经有一套 QQ 群机器人运行时，支持 OneBot 与官方 API 两种接入，但它的回答路径是固定的：收到消息后直接调用宿主的单次对话能力，使用群配置里的系统提示词。它更像一个"全局占位机器人"，没有 Kirara 的人设、记忆与 Orbiter 分工。

本设计要把它变成 Kirara 的入口，而不是再起一个机器人：

- **传输层不动**：连接、重连、验签、群白名单、去重仍由宿主负责。
- **回答者替换**：机器人把归一化后的消息交给 Kirara 编排层，由 Kirara 决定直接回答、调用方块还是交给 Orbiter；回复再沿原通道发回。
- **单实例归属**：同一时间只有一个机器人拥有"回答权"，避免宿主默认机器人与 Kirara 同时回复同一群消息。
- **群与私聊一致**：群聊里被 @ 时回答，私聊时直接回答；两者的会话隔离沿用宿主现有的会话命名规则。
- **可回退**：接管关闭时，机器人回到宿主默认回答路径，不影响已有群配置。

### 5.3 会话与记忆

- UI 与 IM 可以共享同一份人设与长期记忆，但**不共享同一条短期会话流**；群聊上下文不污染私聊。
- 记忆写入属于写级操作，沿用审批语义；IM 触发的写入默认只记录待确认项。
- 记忆的物理位置从包内 `memories/` 迁移到 `api.data_dir`，包目录保持只读。

## 6. 对话走 Orbiter

### 6.1 两条路径

| 路径 | 判定 | 行为 | 用户感受 |
|---|---|---|---|
| 直接对话 | 寒暄、单轮事实问答、简单闲聊 | 人设 + 本地模型流式回答，不调用方块 | 快，像聊天 |
| Orbiter 路径 | 多步骤任务、需要工具/文件/检索、需要更强模型 | 规划 → 调用原子能力 → 润色 → 派发 → 汇总 | 慢一些，但能办事 |

判定优先使用显式信号（用户选择了 Agent 模式、挂了附件、命中任务型动词），再叠加轻量启发式（长度、多步骤连接词、是否需要外部信息）。用户始终可以手动强制走 Orbiter 或强制直接回答。自动判定属于 Orbiter 规划中的"复杂度路由"能力，未落地前以显式信号为准，不假装能自动理解一切。

### 6.2 复杂请求的处理顺序

```text
用户原话
  │
  ├─ 1. 理解与补全：识别目标、约束、交付物、缺失信息
  ├─ 2. 原子能力：按需调用方块（读文件、检索、截图识别、记忆）
  ├─ 3. 提示词工程化：把口语化请求改写成目标/背景/约束/验收标准清晰的简报
  ├─ 4. 目标选择：按任务类型选更合适的云端模型或远程实例
  ├─ 5. 派发与等待：流式接收，向用户显示阶段状态
  └─ 6. 回收与人设化：把结果整理成 Kirara 的语气，保留原始产物的入口
```

关键设计点：

- **润色发生在派发之前**，且只发送工程化简报与必要上下文，不把完整人设、长期记忆和私聊历史整体外发。
- **云端模型是"被调度者"**，不直接面对用户；用户看到的是 Kirara 组织后的回复。
- **原子能力只走方块入口**：不在编排层私接技能或 MOD 工具，确保装备门禁、风险分级与审批不被绕过。
- **失败可解释**：远端不可达、模型拒绝、工具失败都要转成用户能理解的短句，并保留重试与改走本地模型的选项。

### 6.3 与 Orbiter 规划的对应关系

| 本设计需要的能力 | Orbiter 规划中的对应 | 当前状态 |
|---|---|---|
| 简单问答直连 | `direct` 模式 | 宿主已有单次对话能力，可复用 |
| 本地 Agent 处理 | `local_agent` 模式 | 宿主已有 Agent 循环，可复用 |
| 升级到云端/远程 | `remote_agent` 模式与远端调用契约 | 仅设计，未实现 |
| 多目标协同 | `fanout` 模式 | 仅设计，未实现 |
| 自动复杂度判定 | `router=orbiter_auto` | 仅设计，未实现 |

因此本设计的阶段顺序必须尊重一个事实：**Orbiter 没有落地之前，"复杂问题交给 Orbiter"只能以显式选择 + 本地 Agent 的形式存在**，不能把它描述成已经具备的自动能力。

### 6.4 JRVS：行为包的最适配模型

行为包不把 JRVS 当作"云端模型列表里的一个选项"，而是默认的**本地主模型**。定位分三层：

| 层次 | 定位 | 当前状态 | 依据 |
|---|---|---|---|
| 日常对话 | 女仆人格的第一响应者 | 旧应用内已有 | `services/jrvs.py` 中 `system="Kirara"` 触发女仆人格，`MODELS.kiraraModelC` 指向 `televideo-ai/JRVS-7B-1.2.2:latest` |
| 润色 | System 2 草稿/反思后，由 System 1 统一转成 Kirara 口吻 | 旧应用内已有 | `DeepThinkingEngine.polish` 与 `deep_think` 的三段式流程 |
| 编排 | 轻量本地模型负责分诊、补全提示词，复杂任务再交给 Orbiter / 云端 | 仅定位，未实现 | `chat_with_router_details` 目前直接调用 `inference.generate`，返回的 `routing_info` 固定为 `None` |

**为什么它是最适配**

1. **人格原生**：JRVS-7B-1.2.2 "Puff" 用 `system="Kirara"` 直接进入女仆人格，用 `system="JRVS"` 切到冷静助手人格；人格不靠外部长提示词堆出来，行为包只需要声明用哪个人格系统。
2. **适合 24h 常驻**：桌宠与 IM 入口要求"随时在"，本地 Ollama 以 `keep_alive=30m` 驻留，配合常驻进程即可做到入口长期在线；模型不需要每次请求都冷启动，也不依赖外部服务可用性。
3. **本地推理**：`num_gpu=99` 全层卸载、`num_ctx=16384`、Q8 KV 缓存，日常对话与润色都在本机完成，私聊内容与记忆不因一次普通问答而出网。
4. **润色是它的本职**：双系统里 System 2 负责草稿与反思，System 1（JRVS）负责把草稿转成带表情、口头禅的女仆语气；这与"桌宠说人话"的目标天然一致。
5. **编排是它的延伸**：轻量本地模型适合先做"这句话是闲聊还是任务"的分诊，再把复杂任务交给 Orbiter 或更强的云端模型；这一层是定位，不是现状。

**与配置的映射**

`manifest.json` 的 `config.models` 是这套定位的声明处：

| 键 | 值 | 含义 |
|---|---|---|
| `primary` | `jrvs` | 默认本地主模型 |
| `persona_system` | `Kirara` | 走女仆人设的 system 触发词 |
| `runtime.backend` | `ollama` | 本地推理后端 |
| `runtime.model` | `televideo-ai/JRVS-7B-1.2.2:latest` | 与 `services/jrvs.py` 的 `kiraraModelC` 一致 |
| `runtime.context_window` / `gpu_layers` / `kv_cache` / `keep_alive` | `16384` / `99` / `q8` / `30m` | 与旧应用的推理参数一致 |
| `roles.chat` / `roles.polish` / `roles.orchestrate` | `active` / `active` / `planned` | 明确哪一层已经存在、哪一层只是规划 |
| `status` | `declared_not_wired` | 只在配置里声明，尚未接入宿主运行时 |

**现状边界（如实标注）**

- JRVS 目前仍以旧业务形态存在于 `services/jrvs.py`：导入 `chromadb` / `sentence_transformers`，写包内 `memories/`，没有在 SimChat 沙箱内接线。
- 行为包没有注册任何 `jrvs.*` 方块；阶段 1 只注册了 `kirara.trivia`，并通过 `agent.map` 生成一张只读地图（见第 13 节）。没有 `jrvs.ask`、`jrvs.polish` 之类的可调用接口，README 也不把计划写成已实现。
- 编排（router / Orbiter）没有实现；`chat_with_router_details` 的 `routing_info` 恒为 `None`。
- 云端模型与凭据不在本包配置范围内，当前也没有把 `api_client.py` 的云端调用迁进来。
- `config.models.roles.orchestrate=planned` 与 `status=declared_not_wired` 是刻意的：先声明定位，等宿主 Orbiter 与推理服务就绪后再接线。

## 7. 特有 Skill：嘴碎小知识

### 7.1 定位

Kirara 在对话中会主动补充与当前话题相关的冷知识，语气嘴碎、带一点炫耀式的亲昵，例如"主人大人知不知道叉子是 17 世纪才引进泰国的"。这是她的性格标识，不是主回答的一部分。

### 7.2 行为规则

- **不抢答**：先给主回答，再追加一条"小知识"气泡；用户明确说"别废话/赶时间"时当轮关闭。
- **有频率**：同一会话有冷却与每轮上限，避免每句话都插科打诨。
- **可关闭**：用户可在设置里关闭，关闭后不影响主回答；装备门禁同样可以把它卸下。
- **不打断审批**：涉及写级操作、危险操作、错误恢复时，不插入小知识。
- **事实优先**：优先使用包内维护的、带出处的小知识条目；模型自由生成时必须标注"据说/不确定"，并限制在安全题材内（不碰政治、医疗、法律建议、未成年人不宜内容）。
- **与主回答解耦**：小知识失败或超时不影响主回答。

### 7.3 为什么做成方块，而不是只写进提示词

| 维度 | 提示词注入 | 方块（ToolSpec） |
|---|---|---|
| 可控性 | 只能靠模型自觉 | 可装备、可卸载、可单独关闭 |
| 可审计 | 看不到是否触发 | 每次调用都有记录与风险级别 |
| 双入口 | IM 与 UI 各自拼提示词，容易漂移 | 两个入口调用同一个方块 |
| 内容维护 | 散落在提示词里 | 条目与出处可独立维护、可离线 |
| 失败隔离 | 拖累主回答 | 独立超时与降级 |

结论：**性格由人设提示词负责，事实与触发由方块负责**。方块返回一条事实及其出处，编排层负责用 Kirara 的语气说出来。

### 7.4 与现有技能体系的关系

Kirara 包内已经有两套"技能"：`options.json` 的提示词注入，以及 `services/skills/` 的原生技能管理器。本设计不合并、不删除它们，但明确边界：

- 提示词型技能继续作为人设/风格补充。
- 原生技能管理器的工具如果要在 SimChat 的 Agent 循环里可用，必须通过 ToolSpec 方块重新暴露，不能沿用包内旁路。
- "小知识"作为新方块，不依赖上述两套旧机制。

## 8. 与 SimChat 现有契约的对接点与缺口

### 8.1 已经对得上的部分

| 需求 | 现有契约 | 结论 |
|---|---|---|
| 作为 MOD 被加载 | `manifest.json` 的 `id/type/layer/entry/hooks/capabilities/requires`，沙箱执行 `entry(api)` | 已具备；当前包加载为 `loaded`，入口注册 `kirara.trivia` 与只读地图 |
| 能力以方块暴露 | `agent.block` hook、`api.register_tool(ToolSpec)`、宿主 `BLOCK_REGISTRY` 与统一调用入口 | 契约具备；已注册 `kirara.trivia`（read） |
| 地图（AI 实例）生成 | `agent.map` hook、`api.register_agent_preset(...)`、宿主只读实例 | 已具备；Kirara 地图装备 `orbiter` 与 `kirara.trivia` |
| 调用受装备与审批约束 | 装备白名单、风险分级、写级审批挂起 | 契约具备，方块注册后自动继承 |
| 包内静态资源读取 | 沙箱允许读包目录 | 具备，但"能读"不等于"能被浏览器访问" |
| 独立数据目录 | `api.data_dir`、`uploads` 可写 | 具备；`layer=mod` 已分配数据目录 |
| 网络与子进程声明 | `capabilities.net.domains`、`capabilities.shell` | 具备；当前 manifest 已按业务需要声明 |

### 8.2 主要缺口

| 缺口 | 具体表现 | 影响 |
|---|---|---|
| `web.blueprint` 无消费方 | hook 在白名单内，但宿主没有注册 MOD Blueprint 的逻辑，SDK 也没有对应方法 | Kirara 现有的 `/api/kirara/*` 与页面路由无法按契约挂到 SimChat 的 Web 服务上 |
| `ui.slot` / `frontend_entry` 未消费 | 两个字段只被序列化，宿主前端从未读取 | 桌宠浮层没有"官方挂载点"，只能走独立窗口或临时注入 |
| 包目录只读 | 沙箱把包目录设为只读，现有代码习惯写包内 `memories/`、`uploads/`、`audios/`、`videos/` | 直接搬进沙箱会出现权限拒绝；必须迁移到 `data_dir` / `uploads` |
| 能力注册尚未发生 | 当前 `entry(api)` 不注册任何东西 | 物品栏里没有 Kirara 的方块，Agent 也无法调用她 |
| IM 机器人是宿主内建 | 机器人管理器是全局单例，回答路径固定为宿主的单次对话，没有"MOD 接管回答者"的扩展点 | 要接管就必须改宿主契约，或先以配置绑定的方式近似 |
| Orbiter 仅实现显式派发 | 宿主已有 `orbiter` 方块（本地分诊 + 本地润色 + 云端派发 + 审批），但没有调度器、远程调用端点、自动路由、AWS 月租实例与 JRVS-390B | "复杂问题交给 Orbiter"目前指方块级显式派发，不是自动编排 |
| 凭据边界 | 现有业务代码硬编码云端 API Key，未走宿主凭据或服务注入 | 直接搬进沙箱既不安全也不可轮换 |
| 静态资源服务 | 没有 Blueprint 就没有静态路由 | 立绘、按钮、圆球素材无法被前端按 URL 加载 |
| 目录元数据滞后 | SimChat 的 registry 条目仍指向旧仓库路径、旧 id 与旧类型 | 不影响本地加载，但会影响"从目录安装"的体验 |

### 8.3 缺口的分层归属

- **宿主必须补的**：Blueprint 消费方、`ui.slot` 渲染位或等价的前端扩展点、IM 回答者扩展点、Orbiter 调度器与远程调用契约。
- **本包必须补的**：方块注册、数据路径迁移、凭据改为服务注入、静态资源组织。
- **可以绕过的**：桌宠可以先以独立桌面窗口存在，不等待 `ui.slot`；分发可以先以 GitHub 归档存在，不等待 registry 更新。

## 9. 分阶段落地

阶段划分以"依赖关系"为准，不以工时为准。后一阶段不开始，通常是因为前一阶段提供的契约或数据还不存在。

### 阶段 0：MOD 边界（已达成）

包能被加载器校验、依赖解析与沙箱装载，`status=loaded`、无错误；入口不注册任何能力。这一阶段的价值是证明"Kirara 可以作为一个包存在"，而不是证明它有行为。

### 阶段 1：方块化最小闭环

在入口里注册第一批 ToolSpec：至少包含小知识方块，以及一个把复杂请求交给 Orbiter 适配层的方块。此时：

- 物品栏能看到 Kirara 的能力，并能按装备门禁控制。
- UI 对话与 IM 对话都能调用同一个方块，不再各自拼提示词。
- 桌宠尚未出现，IM 仍走宿主默认回答路径。

依赖：阶段 0 的加载边界；宿主的方块注册与调用入口已经存在。

### 阶段 2：对话编排与 Orbiter 对接

建立编排层：统一消息信封、简单/复杂分流、工程化提示词、目标选择与结果回收。此时：

- 简单问答走直接对话；复杂任务显式走 Orbiter 或本地 Agent。
- 云端模型通过 Orbiter 的远程契约接入；在 Orbiter 未落地前，以显式选择本地/远程实例近似。
- 小知识由编排层决定是否追加，而不是由模型随机发挥。

依赖：阶段 1 的方块；宿主 Orbiter 至少具备显式路由与远程调用能力。

### 阶段 3：桌宠前端

把立绘/圆球、气泡、径向按钮、拖动与缩放做出来，先以独立窗口或页面浮层承载。此时：

- 用户能一直看到 Kirara，并通过径向按钮进入对话、能力、记忆与设置。
- 桌宠与工作台共享同一个编排层，不产生第二套会话逻辑。
- 若宿主的 `ui.slot`/Blueprint 消费方仍未就绪，桌宠以独立窗口运行，不阻塞本阶段。

依赖：阶段 2 的编排层与回复流；立绘与圆球素材；静态资源可被前端加载。

### 阶段 4：IM 接管

把宿主的全局机器人回答者切换到 Kirara 编排层，保留传输、重连、白名单与去重。此时：

- 用户在 IM 里 @ 机器人，得到的是 Kirara 的人设与 Orbiter 分工后的回答。
- IM 输入按不可信处理；写级操作只能转交工作台审批。
- 接管可关闭，关闭后回到宿主默认回答路径。

依赖：阶段 2 的编排层；宿主提供"回答者扩展点"或等价的通道绑定能力。若宿主契约未就绪，本阶段只能做"配置层面的近似接管"，不能宣称完成。

### 阶段 5：独立分发与运营

把仓库、Release、依赖说明、安装文档与 registry 条目收口到 GitHub。此时：

- 用户从 GitHub 安装，不依赖自有服务器。
- 版本、ABI、依赖与声明的能力在发布前自检。
- registry 条目与包仓库保持同步，但 registry 不再是唯一入口。

依赖：前四个阶段的包形态稳定；至少一个可用的发行归档。

### 阶段关系

```text
阶段 0 ──▶ 阶段 1 ──▶ 阶段 2 ──┬──▶ 阶段 3 ──┐
                               └──▶ 阶段 4 ──┴──▶ 阶段 5
```

阶段 3 与阶段 4 可以在阶段 2 之后并行；但两者都依赖同一个编排层，否则会出现"UI 一套回答、IM 另一套回答"的分裂。

## 10. 风险与开放问题

| 问题 | 说明 | 倾向 |
|---|---|---|
| 桌宠承载方式 | 浏览器浮层受限于页面生命周期；独立窗口需要额外的桌面壳 | 先独立窗口保证常驻，再争取宿主 `ui.slot` |
| 点击穿透与置顶 | 透明区域穿透、始终置顶、多屏行为在不同系统上差异大 | 作为桌宠的硬指标单独验证，不混在聊天功能里 |
| Blueprint 归属 | 由宿主补消费方，还是包内自带独立 HTTP 服务 | 优先宿主契约；独立服务只作为过渡 |
| IM 接管方式 | 宿主当前机器人是单例且固定回答路径 | 需要明确的"回答者"扩展点，避免两个机器人抢答 |
| 云端模型与隐私 | 工程化简报仍可能包含用户敏感信息 | 默认最小上下文，敏感字段脱敏，提供"仅本地"开关 |
| 凭据管理 | 现有硬编码 Key 不可接受 | 迁移到宿主服务注入或本机加密配置，不进仓库 |
| 小知识的事实准确性 | 模型自由生成容易一本正经地胡说 | 策划条目 + 出处优先；生成内容必须标注不确定性 |
| 立绘与素材授权 | 立绘、Logo、音声的再分发权利需要确认 | 发布前单独核对授权，不把授权问题留到用户侧 |
| 双入口一致性 | UI 与 IM 的人格、记忆、能力容易漂移 | 以编排层为唯一真相，两个入口只做传输适配 |
| 性能与常驻成本 | 桌宠常驻 + 本地模型 + 向量库会争抢资源 | 提供轻量模式：圆球 + 云端模型 + 关闭本地记忆检索 |

## 11. 验收视角（设计层，不是任务清单）

判断这份设计是否被正确落地，看四件事，而不是看代码量：

1. **它是不是一个包**：能安装、能卸载、能升级，卸载后不留下包内写死的状态。
2. **它是不是只有一条能力通路**：UI、IM、Agent 调用的都是同一批方块，装备与审批语义一致。
3. **它是不是一个入口而不是两个产品**：桌宠、工作台、IM 背后是同一个编排层与人设。
4. **它是不是可退化**：Orbiter 不可用时能退回直接对话，云端不可用时能退回本地，立绘不可用时能退回圆球，接管关闭时能退回宿主默认机器人。

## 13. 实现现状（2026-11-19）

### 13.1 已落地：只读地图 + 装备 orbiter

项目术语中「地图」= AI 实例。Kirara 通过新增的 `agent.map` hook 注册一张地图：

- `python/kirara_map.py` 用确定性算法从 `prompts/maid.txt` 派生头像与系统提示：同一份人设文件得到同一张地图，不联网、不伪造模型或服务。
- 系统提示 = 女仆人设原文 + 一段 Orbiter 工具契约（简单问题直接答、复杂问题才派发、每次云端外发需审批、本地 JRVS 不可用时失败关闭、`/@` 与 `/$` 写法）。
- 装备清单固定为 `["orbiter", "kirara.trivia"]`：地图只用宿主 `orbiter` 方块与 Kirara 自己的小知识方块，不枚举其他能力。
- 宿主把预设落盘为 `readonly: true` 的实例：列表中显示「只读」徽标，编辑与删除都会被拒绝；`POST /api/agents/reset` 会保留这类地图并重新创建默认实例。
- 预设按 `mod:<id>` 命名空间幂等同步；重复加载不会重复建实例，MOD 未加载时不会凭空出现地图。

### 13.2 仍未实现（不要当成可用能力）

| 项 | 现状 |
|---|---|
| 自动复杂度路由 | 未实现；分诊由 `orbiter` 方块内部的本地 JRVS 调用完成，不是独立调度器 |
| 远程 `/api/orbiter/call`、`remote_agent`、`fanout` | 仅设计，未实现 |
| AWS 月租实例、虚拟化单租户 | 仅设想，仓库中不存在 |
