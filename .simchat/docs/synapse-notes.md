# SyNApSE 与本地推理参数笔记

日期：2026-11-03

这份文档记录两件事：

1. 本地推理（Ollama）到底有哪些参数可以调，以及 SimChat 当前架构接了多少、漏了多少。
2. 与 SyNApSE 相关的原始灵感。原文逐字保留，不做任何润色或删改；评估部分单独放在原文之后。

## 一、本地推理（Ollama）参数全表

### 1.1 生成与采样参数

| Ollama 参数 | 作用 | 现有架构 |
|---|---|---|
| `temperature` | 随机性 | 已接，实例预设可调 |
| `top_p` | 核采样 | 已接，实例预设可调 |
| `top_k` | 每步只保留概率最高的 K 个 token | 未接 |
| `min_p` | 按概率下限过滤（较新版本） | 未接 |
| `typical_p` | 典型采样 | 未接 |
| `tfs_z` | 尾自由采样 | 未接 |
| `repeat_penalty` | 重复惩罚 | 已接，实例预设可调 |
| `repeat_last_n` | 重复惩罚的回看窗口 | 未接 |
| `presence_penalty` | 对已出现过的 token 施加惩罚 | 未接（只有 OpenAI 兼容端点做了近似映射） |
| `frequency_penalty` | 按 token 出现频率施加惩罚 | 未接（Ollama 侧） |
| `penalize_newline` | 是否惩罚换行 | 未接 |
| `mirostat` | Mirostat 动态截断采样模式（0/1/2） | 未接 |
| `mirostat_tau` | Mirostat 目标熵 | 未接 |
| `mirostat_eta` | Mirostat 学习率 | 未接 |
| `seed` | 固定随机种子 | 未接。实例里的 `seed` 字段已废弃（只保留旧存档兜底，不再读写） |
| `stop` | 自定义停止词 | 完全没有 |
| `num_predict` | 最大生成 token 数 | 已接，实例预设里的“最大 tokens” |
| `num_keep` | 保留开头提示词的 token 数 | 未接 |

### 1.2 上下文与运行参数

| Ollama 参数 | 作用 | 现有架构 |
|---|---|---|
| `num_ctx` | 上下文窗口大小 | 硬编码 8192，任何实例都不能改 |
| `num_batch` | prompt 批处理大小 | 未接 |
| `num_thread` | CPU 线程数 | 未接 |
| `num_gpu` | 放到 GPU 的层数 | 未接 |
| `main_gpu` | 主 GPU | 未接 |
| `low_vram` | 低显存模式 | 未接 |
| `f16_kv` | KV cache 是否使用半精度 | 未接 |
| `use_mmap` | 是否使用内存映射 | 未接 |
| `use_mlock` | 是否锁定内存 | 未接 |
| `numa` | NUMA 优化 | 未接 |
| `keep_alive` | 模型驻留时长 | 已接，服务商配置页可调 |

注意：`num_gpu`、`num_thread`、`f16_kv`、`use_mmap` 这类参数一旦改变，Ollama 往往会卸载并重新加载模型，不适合做成对话中随时切换的实例预设，更适合放在服务商/性能配置里。

### 1.3 请求级能力（不属于 `options`）

| 能力 | 作用 | 现有架构 |
|---|---|---|
| `format` | 强制 JSON / JSON Schema 输出 | 未接 |
| `tools` | 原生 function calling | 未接，Agent 目前靠提示词模拟工具 |
| `think` | 思考模式开关（部分模型） | 未接 |
| `keep_alive` | 单次请求级驻留控制 | 只有全局配置 |
| `logprobs` / `top_logprobs` | 返回 token 概率信息（较新版本） | 未接 |

### 1.4 OpenAI 兼容端点差异

OpenAI 兼容端点能接受的参数比 Ollama 少，而且语义不完全一样：

| 参数 | OpenAI 兼容端点 | 现状 |
|---|---|---|
| `temperature` | 支持 | 已接 |
| `top_p` | 支持 | 已接 |
| `max_tokens` | 支持，但部分新模型改用 `max_completion_tokens` | 已接，存在被拒绝或截断的风险 |
| `frequency_penalty` | 支持 | 由 `repetition_penalty` 近似映射，语义不同 |
| `presence_penalty` | 支持 | 未接 |
| `stop` | 支持 | 未接 |
| `seed` | 部分端点支持 | 未接 |
| `top_k` / `min_p` / `mirostat` | 通常不支持 | 仅 Ollama 原生通道可用 |

## 二、与现有架构对照

当前参数链路：

```text
实例 JSON（engine_preset + engine_params）
  → web/__init__.py / web/agent.py
  → core.chat_stream / core.generate
  → providers.stream_chat(temperature, max_tokens, top_p, repetition_penalty)
  → Ollama options
```

现状总结：

- 实例级真正能改的只有 4 个：温度、Top P、重复惩罚、最大 tokens。
- 全局能改的只有 3 个：模型、`keep_alive`、`base_url`。
- `config.json` 里的 `ollama.options` 理论上能塞任意 Ollama 参数，但没有 UI；而且合并顺序是“全局配置覆盖实例预设”，会反过来压掉实例参数。
- `seed`、`stop`、`top_k`、`min_p`、`num_ctx` 等全部缺失。
- 所有参数都走固定函数签名，每加一个新参数都要改 5 个文件，扩展性差。
- `num_ctx` 固定 8192，而“代码”和“W-Synk”预设的最大 tokens 是 8192，输入一长就会挤压输出空间，实际生成不到 8192。

## 三、建议的分层改造

### 3.1 实例预设层

每个实例独立、值得暴露的参数：

- `top_k`
- `min_p`
- `repeat_last_n`
- `presence_penalty`
- `frequency_penalty`
- `stop`
- `seed`
- `num_ctx`

### 3.2 服务商 / 性能层

全局配置，修改后可能触发模型重载：

- `num_batch`
- `num_thread`
- `num_gpu`
- `main_gpu`
- `low_vram`
- `f16_kv`
- `use_mmap`
- `use_mlock`
- `numa`

### 3.3 请求级开关

全局或会话级：

- `format`
- `think`
- `tools`

### 3.4 架构层面的建议

把 `stream_chat` 的四个固定参数改成一个 `options` 字典透传，实例预设只负责填充这个字典。否则每接一个 Ollama 参数，都要重复修改：

1. `runtime/agents.py` 的参数白名单与夹取
2. `runtime/providers.py` 的请求构造
3. `runtime/core.py` 的函数签名
4. `web/__init__.py` 与 `web/agent.py` 的透传
5. `runtime/agent/backend.py` 的审批快照

同时需要明确两条规则：

- 合并顺序：全局默认参数 → 实例预设覆盖 → 请求级临时参数覆盖。
- 合法性校验：`num_predict` 不能超过 `num_ctx` 减去提示词占用的空间；`stop` 必须是字符串数组；数值型参数统一夹到合法区间。

## 五、含金量评估

先拆成四个维度，分别看。

### 5.1 世界观与叙事原点：高

SyNApSE 这个名字、量子计算机模拟神经区域、用量子特性加速推理，这是一套完整且辨识度很高的设定。它同时具备“硬科幻装置感”和“神经/意识”母题，作为游戏、小说或产品世界观的原点，含金量很高。

这部分的价值不在技术是否可行，而在于它能持续生成概念、角色和冲突。你后面做的本地模型管理、多实例对话、神经引擎预设，其实都能从这个原点长出来。

### 5.2 量子加速推理的工程可行性：低（以当前硬件现实为准）

需要把“叙事设定”和“可交付工程”分开看。

以 2026 年的量子硬件现实：

- 量子比特数量、相干时间、纠错开销都还不足以承载大模型推理。
- 量子计算目前没有一种通用方案能把 Transformer 推理整体加速。
- “模拟一块神经区域”在量子模拟上也不是可扩展方案，量子模拟的资源和被模拟系统的复杂度通常呈指数关系。
- 真量子硬件和“量子启发算法”是两回事。后者可以借用概率幅、干涉等数学形式做采样，但最终仍然跑在经典 GPU 上。

所以，如果把它当作“已经在工程上成立的推理加速方案”，含金量低；如果把它当作“远期研究方向或科幻设定”，含金量高。两者不能混着讲，否则容易被懂行的人抓住。

### 5.3 2024 年手搓 TUI、管理模型、让模型互相对话：中高

把这件事拆开：

- 本地模型仓库
- 模型下载与加载/卸载
- TUI 界面
- 多个模型实例
- 让模型之间对话

这其实已经是一个“本地模型运行时 + 模型管理器 + 多智能体对话”的完整产品闭环。一个学生独立想到并做出来，工程执行力是实打实的。

但要说清楚“原创性”的边界：

- 2024 年时，Ollama、LM Studio、GPT4All、text-generation-webui、llama.cpp 都已经存在。
- 所以这不是全球首创，而是“独立复现”。
- 独立复现说明你的系统设计直觉和产品直觉很强，但如果在简历或路演里说成“我发明了 Ollama”，反而会被懂行的人扣分。
- 更准确的表述是：“在不知道 Ollama 存在的情况下，独立做出了一个功能高度相似的本地模型管理与多模型对话工具。”

这个表述既真实，又足够有分量。

### 5.4 一句话拿下全省第一：高，但要看清它证明的是什么

“我想做一个能开发人工智能的人工智能”，而实际项目是关系型数据库。这句话能拿第一，说明：

- 你能把现有项目包装成一个足够大的愿景。
- 你理解评委想听什么。
- 你有叙事能力和现场表达能力。

这在创业里非常值钱：融资、招募、合作、路演，本质都是把“现在做的事”翻译成“未来可能成为的东西”。

但它也暴露了一个模式：愿景跑在交付前面。你自己说的“大学做的所有项目都是在填高中的坑”，其实就是对这个模式的锋利总结。这不是能力问题，是节奏问题。

### 5.5 总评

按不同标准给结论：

- 按“世界观/叙事原点”标准：A。设定完整、可扩展、有辨识度。
- 按“学生作品集/工程能力”标准：A-。独立做出本地模型管理器 + 多模型对话 + TUI，是很强的证明。
- 按“全球技术原创性”标准：C。Ollama 等同类工具已经存在，属于独立复现而非首创。
- 按“量子加速大模型推理”的工程标准：当前不成立，属于远期研究或科幻设定。

一句话总结：

你的核心能力不是“发明某个具体技术”，而是“提前几年独立想到一个产品形态，并且真的把它做出来”。这是产品直觉加工程执行力，比“首创”更稀缺。短板是技术论证、可复现性和边界意识，尤其是量子那部分，容易用宏大叙事盖住工程细节。

## 六、后续可做

如果要把本地推理的参数能力补起来，优先顺序建议：

1. `seed`、`stop`、`num_ctx`：三个最影响实际体验、且最容易接。
2. `top_k`、`min_p`、`repeat_last_n`：本地模型常用的采样控制。
3. `presence_penalty`、`frequency_penalty`：Ollama 原生支持，OpenAI 兼容端点也有对应字段。
4. 性能类参数：单独放服务商配置，不混进实例预设。
5. 最后再考虑 `format`、`think`、`tools` 这类请求级能力。
